# Identity and session

Renglo identity is **AWS Cognito**. A person signs in to the console, receives JWTs, and every authenticated API call presents that JWT. Renglo then maps the Cognito username onto a **stable user id** and a **user entity** in DynamoDB.

This document covers that path only: who the caller is, how the session is stored, and how Core resolves the current user. It does not cover portfolios, teams, the auth tree, or `authorize()`. Those are tenancy and authorization, not identity.

## 1. Mental model

Three records describe a person:

| Layer | Where it lives | What it is |
|---|---|---|
| **Cognito user** | AWS Cognito user pool | Email, password, `given_name`, `family_name`, tokens |
| **User id** | Derived, never stored as a secret | First 9 hex chars of `md5(cognito username)` |
| **User entity** | DynamoDB entity table | Profile document keyed by that user id |

Cognito is the source of truth for *authentication* (proof of identity). The user entity is the source of truth for *profile data that Renglo owns* (name, email copy, last IP, tags). The user id is the join key used everywhere else (teams, sessions, files, extensions).

Renglo does **not** keep a server-side login session cookie for the API. Flask-Cognito validates the Bearer JWT on each request. The console keeps tokens in `sessionStorage`.

```
┌─────────────┐     USER_PASSWORD_AUTH      ┌──────────────────┐
│   Console   │ ──────────────────────────► │  Cognito pool    │
│  (Vite app) │ ◄── Id / Access / Refresh ── │  (email alias)   │
└──────┬──────┘                             └────────┬─────────┘
       │  Authorization: Bearer <id or access JWT>   │
       ▼                                             │
┌─────────────┐   flask_cognito verifies JWT         │
│  renglo-api │ ◄────────────────────────────────────┘
│  /_auth/*   │
└──────┬──────┘
       │  user_id = md5(username)[:9]
       ▼
┌─────────────┐
│  DynamoDB   │  irn:entity:user:*  /  _id = user_id
│  entity tbl │
└─────────────┘
```

## 2. Architecture

| Piece | Repository | Responsibility |
|---|---|---|
| User pool + app client | `ops/launcher/cdk/stacks/auth.py` | Provision Cognito |
| Sign-in, tokens, forgot-password | `console/src/components/console/authService.ts`, `authSession.ts` | Client Cognito SDK |
| JWT gate on HTTP | `renglo-api` + `flask_cognito` | Reject missing/invalid Bearer tokens |
| User entity + Cognito admin API | `renglo.auth.auth_controller` / `auth_model` | Profile, lookup, create, update |
| Framework-neutral claims | `renglo.runtime` | Read JWT in Flask; forward claims to Lambda/Docker handlers |

`renglo-lib` has no Flask routes. Identity HTTP lives on the `app_auth` blueprint (`url_prefix='/_auth'`).

## 3. Cognito user pool

Provisioned by `AuthStack`. Defaults that matter for identity:

| Setting | Value | Why |
|---|---|---|
| `self_sign_up_enabled` | `False` | New users come from team invite or admin create, not public register |
| Sign-in alias | email | Username for `InitiateAuth` is the email address |
| Auto-verify | email | Invite/admin-create paths mark email verified |
| Required attribute | email (mutable) | Profile email can change in Cognito |
| Auth flows | `USER_PASSWORD_AUTH`, `USER_SRP_AUTH` | Console uses `USER_PASSWORD_AUTH` |
| App client secret | none | Public SPA client |
| Token validity | 1–24 hours (default **24**) | Access and id tokens; from `platform_defaults.json` → `cognito.token_validity_hours` |

Admin-created users (bootstrap operators) receive Cognito’s invitation email with a **temporary password** and a console link:

```
{console_setup_base_url}invite?setup=admin&email={username}
```

That path is Cognito `NEW_PASSWORD_REQUIRED`, not the team-invite hash. Team invitees set a **permanent** password when they accept, so first login has no challenge.

OAuth (authorization code + OpenID/email/profile) is configured when callback URLs are supplied. Local callbacks include `http://localhost:5173/` and `http://localhost:5173/callback`. Day-to-day console login does not use the Hosted UI; it calls Cognito directly.

### Cognito user states you will see

| State | How they got there | First login |
|---|---|---|
| `CONFIRMED` | Team invite (`cognito_user_create_with_permanent_password`) | Normal `USER_PASSWORD_AUTH` |
| `FORCE_CHANGE_PASSWORD` | `AdminCreateUser` with a temporary password (admin setup) | `NEW_PASSWORD_REQUIRED` challenge |
| Does not exist | Email never invited / created | Sign-in fails |

Forgot-password is blocked by Cognito while the user is in `FORCE_CHANGE_PASSWORD`. The console sends those users back to `/invite?setup=admin`.

## 4. Console session

After a successful `InitiateAuth`, Cognito returns three tokens. The console stores them in **`sessionStorage`** (tab-scoped, not cookies):

| Key | Token | Typical use |
|---|---|---|
| `idToken` | OpenID id token | Profile claims (`email`, `given_name`, `family_name`); often sent as `Authorization` |
| `accessToken` | Access token | `username` claim; API Bearer token |
| `refreshToken` | Refresh token | Stored; console does not currently expose a refresh helper in `authService.ts` |
| `token_exp` | Id token `exp` | Client-side expiry |
| `cu_handle` | `md5(accessToken.username).substring(0, 9)` | Same algorithm as Core user id |
| `cu_email`, `cu_first`, `cu_last` | From id token (with profile fallbacks) | UI chrome |

Sign-in (`authService.signIn`):

```ts
const params = {
  AuthFlow: AuthFlowType.USER_PASSWORD_AUTH,
  ClientId: import.meta.env.VITE_COGNITO_APP_CLIENT_ID,
  AuthParameters: {
    USERNAME: username,  // email
    PASSWORD: password,
  },
};
```

Two outcomes:

1. `AuthenticationResult` — tokens are stored; `finishAuthenticatedSession` runs.
2. `NEW_PASSWORD_REQUIRED` — login page does **not** complete the challenge. Admin setup belongs on `/invite?setup=admin`. Team invitees should already be `CONFIRMED`.

`finishAuthenticatedSession` then **upserts the user entity** so DynamoDB exists even on first login of a Cognito-only user:

```http
PUT {VITE_API_URL}/_auth/user
Authorization: Bearer {idToken}
Content-Type: application/json

{ "last_login": true }
```

Optional body fields: `name`, `slot_a` (last name), `email`. The **user id is never taken from the body**. The API hashes it from the JWT.

On success the console navigates to `/home`.

### Console environment

| Variable | Purpose |
|---|---|
| `VITE_COGNITO_REGION` | Cognito SDK region |
| `VITE_COGNITO_APP_CLIENT_ID` | Public app client |
| `VITE_API_URL` | renglo-api base URL (no trailing `/_auth`) |

## 5. API JWT authentication

`create_app()` constructs `CognitoAuth(app)` after loading config. Flask-Cognito reads:

```python
COGNITO_REGION
COGNITO_USERPOOL_ID
COGNITO_APP_CLIENT_ID
COGNITO_CHECK_TOKEN_EXPIRATION  # default True
```

Protected routes use:

```python
from flask_cognito import cognito_auth_required, current_cognito_jwt

@app_auth.route('/user', methods=['GET'])
@cognito_auth_required
def get_user():
    ...
```

The client must send:

```http
Authorization: Bearer <jwt>
```

Either an **id token** or an **access token** is accepted. Claim names differ (see [User id](#6-user-id)).

On success, `current_cognito_jwt` is a dict of claims. `renglo.runtime.get_current_jwt_claims()` copies that dict when a Flask app context exists, so `renglo-lib` does not import Flask-Cognito at module load.

Unauthenticated exception: **`PUT /_auth/user/invite`** (accept team invite). That caller is proving inbox access with `code` + `email`, not a JWT.

`JWKS_URL` is built when the auth blueprint loads:

```text
https://cognito-idp.{region}.amazonaws.com/{userPoolId}/.well-known/jwks.json
```

It is not read by route handlers; Flask-Cognito fetches JWKS itself.

### Legacy `login_required`

`renglo.auth.login_required` redirects to `app_auth.login` when Flask `session` has no `id_token`. The `/_auth` API does not use it. Treat it as leftover session-cookie code, not the current identity path.

## 6. User id

### Algorithm

```python
# renglo.common.create_md5_hash
hashlib.md5(input_string.encode('utf-8')).hexdigest()[:num_digits]
```

For people, `num_digits` is **9**. The console uses the same function (CryptoJS MD5, first 9 hex chars).

### Which string is hashed?

From a JWT (`AuthController._user_id_from_claims` and the `/_auth/user` routes):

| Token | Claim used | Typical value |
|---|---|---|
| Id token | `cognito:username` | Cognito username (often the email when `AdminCreateUser` used email as username) |
| Access token | `username` | Same Cognito username |

```python
if "cognito:username" in claims:
    return create_md5_hash(claims["cognito:username"], 9)
if "username" in claims:
    return create_md5_hash(claims["username"], 9)
return None
```

The team-invite accept path hashes `AdminCreateUser`’s `User.Username` the same way, then writes the user entity with that `_id`.

### Example

If Cognito username is `ada@example.com`:

```text
md5("ada@example.com") = 3e3417d7ef77d5932a6734b916515ed5
user_id                = 3e3417d7e
```

```python
from renglo.common import create_md5_hash
create_md5_hash("ada@example.com", 9)  # "3e3417d7e"
```

### Lookup by email (invite existing user)

`AuthController.get_user_id(email)` is **not** exposed on the HTTP API. It lists Cognito users filtered by email, reads the **`sub`** attribute, and hashes **`sub`**, not username.

That is a different input than the JWT path. If username ≠ `sub` (common when email is only an alias and Cognito generated a UUID username), `get_user_id` and `get_current_user()` can disagree. Callers adding an existing pool user to a team go through this lookup.

Do not expose `get_user_id` as a public endpoint; it is an internal invite helper.

## 7. User entity

### Keys

| Field | Value |
|---|---|
| `index` (partition) | `irn:entity:user:*` |
| `_id` (sort) | `user_id` (9-char hash) |
| `irn` | `irn:entity:user:{user_id}` |
| `type` | `user` |

Users are global. They are not nested under a portfolio.

### Fields written at create

`AuthController.create_entity('user', ...)` stores a standard entity envelope:

| Field | Source |
|---|---|
| `_id` | `user_id` from kwargs (not a new UUID) |
| `name` | first name |
| `slot_a` | last name |
| `email` | email |
| `handle`, `about`, `location`, `slot_b`–`slot_e` | optional / empty |
| `owner_id` | same `user_id` |
| `last_ip` | `X-Forwarded-For` or `remote_addr` on `PUT /_auth/user` |
| `language` | `Accept-Language` |
| `tags` | dict, sanitized |
| `is_active` | `True` |
| `added`, `modified`, `last_login` | ISO timestamps |
| `raw_id` | unused UUID (user `_id` is still the Cognito-derived hash) |

There is **no** `POST /_auth/user`. Creation is a side effect of `PUT /_auth/user` when the entity is missing (`create_user_funnel`).

### Partial updates

`PUT /_auth/user` merges `payload` into the existing document. Empty `name` / `slot_a` / `email` on the entity are filled from JWT claims when the JWT has them.

`PUT /_auth/user/profile` is the dedicated first/last-name write: it updates DynamoDB **and** Cognito `given_name` / `family_name`. Both names are required (non-empty after strip). If Cognito fails after DynamoDB succeeds, the API returns that failure with a message that the database write already happened.

## 8. Current-user resolution

`AuthController.get_current_user(jwt_claims=None)` is the Core API every controller and handler should use.

Precedence:

1. **`jwt_claims` argument** — explicit claims dict
2. **`_invocation_user_id`** — set by `set_invocation_user` (ingress, impersonation, tests)
3. **`_invocation_jwt_claims`** — set by `set_invocation_jwt_claims` (Lambda/Docker payload)
4. **Runtime adapter** — `get_current_jwt_claims()` → Flask-Cognito in an app context
5. **`None`** — not authenticated

```python
def get_current_user(self, jwt_claims=None):
    if jwt_claims is not None:
        uid = self._user_id_from_claims(jwt_claims)
        if uid is not None:
            return uid
    if getattr(self, "_invocation_user_id", None) is not None:
        return self._invocation_user_id
    if getattr(self, "_invocation_jwt_claims", None) is not None:
        uid = self._user_id_from_claims(self._invocation_jwt_claims)
        if uid is not None:
            return uid
    claims = get_current_jwt_claims()
    uid = self._user_id_from_claims(claims)
    if uid is not None:
        return uid
    return None
```

Extension handlers typically do:

```python
user_id = self.AUC.get_current_user()
if not user_id:
    return {"success": False, "message": "Authentication required", "status": 401}
```

`SessionController.get_current_user()` duplicates the claim hashing and falls back to `md5("anonymous")` when no claims exist. Prefer `AuthController.get_current_user()` for new code so a missing JWT is `None`, not a fake anonymous id.

Route helpers in `auth_routes.get_current_user()` still hash `current_cognito_jwt` directly. That helper is marked **will deprecate** in favor of `AuthController.get_current_user()`.

## 9. HTTP API

Base path: `/_auth`. All routes below except invite-accept require `@cognito_auth_required`.

Route-level `authorization_check(...)` currently always returns success. Identity still requires a valid JWT.

### `GET /_auth/user`

Returns the signed-in user’s entity.

**Success (200):** the document itself (not wrapped in `{success, document}`).

```json
{
  "_id": "a1b2c3d4e",
  "index": "irn:entity:user:*",
  "irn": "irn:entity:user:a1b2c3d4e",
  "type": "user",
  "name": "Ada",
  "slot_a": "Lovelace",
  "email": "ada@example.com",
  "is_active": true,
  "tags": {},
  "last_ip": "203.0.113.10",
  "language": "en-US,en;q=0.9",
  "added": "2026-09-01T12:00:00.000000",
  "modified": "2026-09-15T16:00:00.000000",
  "last_login": "2026-09-15T16:00:00.000000"
}
```

**Missing entity (404):**

```json
{
  "success": false,
  "message": "Entity not found",
  "status": 404
}
```

First login should have created the document via `PUT`. A 404 means `PUT /_auth/user` never succeeded for this username hash.

### `PUT /_auth/user`

Upsert. User id, name, last name, and email are taken from the JWT, not the URL. Body is a partial document.

```http
PUT /_auth/user HTTP/1.1
Authorization: Bearer eyJraWQiOi...
Content-Type: application/json
Accept-Language: en-US
X-Forwarded-For: 203.0.113.10

{
  "last_login": true,
  "tags": { "locale": ["en"] }
}
```

**Success (200):**

```json
{
  "success": true,
  "message": "Entity updated",
  "document": { "_id": "a1b2c3d4e", "...": "..." },
  "status": 200
}
```

If the entity did not exist, the same status is returned after `create_user_funnel`.

Injection-unsafe string values in the body are dropped by `validate_payload` on other routes; this PUT passes `payload` through after sanitizing `tags` only.

### `PUT /_auth/user/profile`

Updates first and last name in DynamoDB and Cognito.

```json
{
  "first": "Ada",
  "last": "Lovelace"
}
```

Aliases: `name` for first, `slot_a` for last. Both must be non-empty.

**Success (200):** `{ "success": true, "message": "Profile updated", "document": { ... }, "status": 200 }`

**Validation (400):** `"First and last name are required"`

### `GET /_auth/user/token`

Echoes the raw JWT from `Authorization`. Useful for debugging which token the client sent.

```json
{ "success": true, "output": "eyJraWQiOi..." }
```

**400** if the header is missing or not `Bearer ...`.

### `GET /_auth/`

Authenticated no-op. Returns `{ "message": "" }`.

## 10. Cross-runtime identity

HTTP is not the only place Core runs. Schd can invoke extension handlers in-process, on Lambda, or in Docker. Those processes have no Flask-Cognito request.

### Forward claims from the API

`attach_jwt_claims_to_payload(payload)` copies `current_cognito_jwt` onto `payload["_jwt_claims"]` if the key is not already set.

### Apply claims on the handler

`apply_handler_invocation_context(handler, payload)`:

1. Pops `_jwt_claims` so handlers do not persist it
2. Calls `set_invocation_jwt_claims(claims)` on `handler.AUC`, `handler.CHC`, and `handler.SHC` when present
3. **Always** resets invocation claims, even when the key is absent, so a warm Lambda container cannot reuse the previous caller

`get_current_user()` on that handler’s `AuthController` then hashes the forwarded claims.

### Server-resolved roles (not identity, but same payload)

`attach_auth_roles_to_payload` always overwrites `payload["_auth_roles"]`. Clients cannot forge roles. Identity is still the JWT; roles come from the auth tree after `authorize()`.

### Ingress / impersonation

`set_invocation_user(user_id)` bypasses JWT hashing and pins a Renglo user id (webhook or channel paths that already resolved the person).

## 11. Cognito admin operations

Used by Core, not by the browser SDK. Implemented on `AuthModel` with `boto3` `cognito-idp`.

| Method | Cognito API | When |
|---|---|---|
| `check_user_by_email` | `list_users` filter `email = "..."` | Invite: is this email already in the pool? |
| `cognito_user_create` | `admin_create_user` + temp password, `MessageAction=SUPPRESS` | Create in `FORCE_CHANGE_PASSWORD` without sending Cognito’s email |
| `cognito_user_create_with_permanent_password` | create + `admin_set_user_password(Permanent=True)` | Team invite accept; user is `CONFIRMED` |
| `cognito_user_delete` | `admin_delete_user` | Rollback if permanent password set fails after create |
| `cognito_user_permanent_password_assign` | `admin_set_user_password` | Assign/replace a permanent password |
| `cognito_update_user_attributes` | `admin_update_user_attributes` | Profile first/last name |
| `cognito_user_login_challenge` | `admin_initiate_auth` + `NEW_PASSWORD_REQUIRED` | **Not used.** Admin challenge is completed in the console (`authInvite`) |

Temporary passwords generated for `AdminCreateUser` satisfy Cognito’s default policy (upper, lower, digit, symbol, length 20).

Invite accept does **not** return tokens. The API returns 200 and the console sends the user to sign in, so they learn the login screen.

## 12. Password recovery and first-time setup

These flows talk to Cognito from the **console**. They are not `/_auth` routes.

| Console route | Cognito API | Notes |
|---|---|---|
| `/` login | `InitiateAuth` `USER_PASSWORD_AUTH` | Stores tokens; `PUT /_auth/user` |
| `/invite?setup=admin` | `InitiateAuth` then `RespondToAuthChallenge` `NEW_PASSWORD_REQUIRED` | Bootstrap admin with temp password from Cognito email |
| `/invite?code=&email=` | `PUT /_auth/user/invite` | Team invite; no JWT required |
| `/forgot` | `ForgotPassword` | Blocked while `FORCE_CHANGE_PASSWORD` |
| `/reset` | `ConfirmForgotPassword` | Email + code + new password |

Public `SignUp` / `ConfirmSignUp` helpers exist in `authService.ts`, but the pool has **self-sign-up disabled**. Treat register/confirm UI as inactive unless a pool is later opened.

## 14. Worked examples

### 14.1 Sign in (console equivalent)

```python
import boto3

client = boto3.client("cognito-idp", region_name="us-east-1")
resp = client.initiate_auth(
    ClientId=COGNITO_APP_CLIENT_ID,
    AuthFlow="USER_PASSWORD_AUTH",
    AuthParameters={"USERNAME": "ada@example.com", "PASSWORD": "..."},
)
id_token = resp["AuthenticationResult"]["IdToken"]
access_token = resp["AuthenticationResult"]["AccessToken"]
```

### 14.2 Call Core as that user

```bash
export TOKEN='eyJraWQiOi...'   # id or access token

# Upsert profile / first login
curl -sS -X PUT "$API/_auth/user" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"last_login": true}'

# Read user entity
curl -sS "$API/_auth/user" \
  -H "Authorization: Bearer $TOKEN"

# Update names (DynamoDB + Cognito)
curl -sS -X PUT "$API/_auth/user/profile" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"first":"Ada","last":"Lovelace"}'
```

### 14.3 Resolve user id in a handler

```python
from renglo.auth.auth_controller import AuthController

class MintLink:
    def __init__(self, config):
        self.AUC = AuthController(config=config)

    def run(self, payload):
        user_id = self.AUC.get_current_user()
        if not user_id:
            return {"success": False, "message": "Authentication required", "status": 401}
        # user_id is the 9-char hash used as irn:entity:user:{user_id}
        ...
```

In Flask, this works because `get_current_jwt_claims()` reads the request JWT. In Lambda, the host must have already called `apply_handler_invocation_context` (or `set_invocation_jwt_claims` / `set_invocation_user`).

### 14.4 Pin identity without a JWT (tests / ingress)

```python
auc = AuthController(config=config)
auc.set_invocation_user("a1b2c3d4e")
assert auc.get_current_user() == "a1b2c3d4e"
```

### 14.5 Decode which token you have

Id token payload includes `cognito:username`, `email`, `given_name`, `family_name`, `aud` (app client id).

Access token payload includes `username`, `client_id`, `scope`; it typically **omits** `email` and `given_name`. `PUT /_auth/user` still runs, but name/email backfill from JWT will be empty unless the client sent an id token (as `finishAuthenticatedSession` does).
