# Tenancy model (entities)

Renglo tenancy is a **graph of five entity types** stored in DynamoDB. A **user** is a person (see [Identity and session](identity-and-session.md)). A **portfolio** is the tenant. **Orgs**, **teams**, and **tools** live under that portfolio.

This document is the entity model: what each type is, how it is keyed (IRN), how it is created and updated, and which HTTP routes manage it. Membership and grants are **relationships** (`user:team`, `team/tool:org`, …). They are introduced here only as far as they explain why entities exist. The compiled view of those rels is the auth tree; enforcement is `authorize()`. Those are separate documents.

## 1. Mental model

```
                         ┌──────────┐
                         │   User   │  global person (Cognito-derived id)
                         └────┬─────┘
                              │  member of (rels, not nesting)
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  Portfolio  (tenant / workspace)                            │
│                                                             │
│   ┌─────────┐    ┌─────────┐    ┌────────────────────────┐  │
│   │  Team   │    │   Org   │    │  Tool (installed copy) │  │
│   │ Admin,  │    │ building│    │  data, schd, …         │  │
│   │ Ops, …  │    │ / unit  │    │  + role catalog        │  │
│   └─────────┘    └─────────┘    └────────────────────────┘  │
│                                                             │
│   Grants are assigned to teams, never to users directly.    │
└─────────────────────────────────────────────────────────────┘
```

| Entity | What it is | Nesting |
|---|---|---|
| **User** | A person. Identity lives in Cognito; this is the Renglo profile. | Global. Not owned by a portfolio. |
| **Portfolio** | The tenant. Billing, branding, and “which workspace am I in?” | Global. Has no parent. |
| **Org** | An operating unit inside a portfolio (a building, a brand, a site). Application data is scoped `(portfolio, org, ring)`. | Child of a portfolio (encoded in the IRN). |
| **Team** | A group of users. **All grants hang off teams.** | Child of a portfolio (IRN) plus a `team:portfolio` rel for graph walks. |
| **Tool** | An **installed instance** of a system extension (`data`, `schd`, …), including that tool’s role catalog. | Child of a portfolio. Not a new product; a link to an existing system tool. |

A user can belong to many portfolios by sitting on teams in each. There is no `user:portfolio` rel. Portfolio membership is always `user → team → portfolio`.

Creating a portfolio does **not** create a default org. It creates an **Admin** team and puts the creator on that team. Orgs and tools are added later.

## 2. Storage

Two DynamoDB tables, provisioned in `ops/launcher/cdk/stacks/storage.py`:

| Config key | Table | Keys | Holds |
|---|---|---|---|
| `DYNAMODB_ENTITY_TABLE` | `{env}_entities` | `index` (PK) + `_id` (SK) | Entity documents |
| `DYNAMODB_REL_TABLE` | `{env}_rel` | `index` (PK) + `rel` (SK) | Graph edges |

`AuthModel` talks to both. Entity I/O is `get_item` / `put_item` / `query` on the entity table. Relationships are a separate document type (`{index, rel}`) and are **not** nested inside entity JSON.

There is no SQL foreign key. Nesting is a convention on the partition key (see IRN). DynamoDB cannot mutate a primary key, so “moving” or “soft-deleting” an entity means **write a copy under a new `index`, then delete the original**.

## 3. IRN and DynamoDB keys

Every entity has:

| Field | Role |
|---|---|
| `index` | DynamoDB partition key. A queryable type+container prefix. |
| `_id` | DynamoDB sort key. The entity id. |
| `irn` | Canonical resource name (not the Dynamo key). Unique string for logs and references. |

Pattern:

```text
index  = irn:entity:{container?}{type}:{container_id?}{/* or *}
_id    = {entity_id}
irn    = irn:entity:{path}:{entity_id}
```

| Type | `index` (PK) | `_id` (SK) | `irn` |
|---|---|---|---|
| user | `irn:entity:user:*` | 9-char hash of Cognito username | `irn:entity:user:{user_id}` |
| portfolio | `irn:entity:portfolio:*` | 12-char hash of a new UUID | `irn:entity:portfolio:{portfolio_id}` |
| org | `irn:entity:portfolio/org:{portfolio_id}/*` | 12-char hash of a new UUID | `irn:entity:portfolio/org:{portfolio_id}/{org_id}` |
| team | `irn:entity:portfolio/team:{portfolio_id}/*` | 12-char hash of a new UUID | `irn:entity:portfolio/team:{portfolio_id}/{team_id}` |
| tool | `irn:entity:portfolio/tool:{portfolio_id}/*` | 12-char hash of a new UUID | `irn:entity:portfolio/tool:{portfolio_id}/{tool_id}` |

Wildcard in `index` is literal. Listing every org in a portfolio is:

```python
entity_table.query(
    KeyConditionExpression=Key('index').eq(
        f"irn:entity:portfolio/org:{portfolio_id}/*"
    )
)
```

That is why orgs and teams do **not** need `portfolio:org` / `portfolio:team` rels to list children. The parent id is in the partition key.

Portfolios **cannot** be listed that way: they share one global index (`irn:entity:portfolio:*`), so a query would return every tenant in the table. A user’s portfolios are discovered by walking `user:team` then `team:portfolio`.

### Id generation

```python
# renglo.common.create_md5_hash
hashlib.md5(input_string.encode("utf-8")).hexdigest()[:num_digits]
```

| Type | Length | Input |
|---|---|---|
| user | 9 | Cognito username (`cognito:username` or `username`) |
| portfolio, org, team, tool | 12 | `str(uuid.uuid4())` at create time |

`raw_id` on the document is the UUID **before** hashing. `_id` is the hash. For users, `_id` is the Cognito-derived id; `raw_id` is still a fresh UUID and is unused as a key.

Ids are hex, so they contain no hyphens. Composed URL ids ` {portfolio_id}-{org_id}` split on the **first** hyphen are therefore unambiguous.

## 4. Shared document envelope

`AuthController.create_entity` writes the same envelope for every type:

```python
data = {
    "_id": sk,
    "name": kwargs.get("name", ""),
    "about": kwargs.get("about", ""),
    "handle": kwargs.get("handle", ""),
    "location": kwargs.get("location", ""),
    "email": kwargs.get("email", ""),
    "slot_a": kwargs.get("slot_a", ""),   # last name on users
    "slot_b": kwargs.get("slot_b", ""),
    "slot_c": kwargs.get("slot_c", ""),
    "slot_d": kwargs.get("slot_d", ""),
    "slot_e": kwargs.get("slot_e", ""),
    "owner_id": kwargs.get("user_id", ""),
    "added": datetime.now().isoformat(),
    "is_active": True,
    "type": type,                         # "user" | "portfolio" | "org" | "team" | "tool"
    "last_ip": kwargs.get("ip", ""),
    "last_login": datetime.now().isoformat(),
    "modified": datetime.now().isoformat(),
    "raw_id": raw_id,
    "index": pk,
    "irn": irn,
    "language": kwargs.get("lan", ""),
    "tags": kwargs["tags"] if isinstance(kwargs.get("tags"), dict) else {},
}
if type == "tool":
    data["roles"] = self._normalize_roles_list(kwargs.get("roles"))
```

`modified` is refreshed on every `put_item` in the model.

Unused slots (`slot_b`–`slot_e`, `location`) are present so the console and older clients can store extra strings without a schema migration. Treat them as optional.

## 5. User

Covered in depth in [Identity and session](identity-and-session.md). Tenancy-relevant facts:

- Global: `index = irn:entity:user:*`. A user is not “in” a portfolio.
- `_id` is **not** a random 12-char id; it is `md5(cognito_username)[:9]`.
- No `POST /_auth/user`. First write is `PUT /_auth/user` (upsert / `create_user_funnel`).
- Access to a portfolio is **only** through team membership.

```json
{
  "_id": "3e3417d7e",
  "index": "irn:entity:user:*",
  "irn": "irn:entity:user:3e3417d7e",
  "type": "user",
  "name": "Ada",
  "slot_a": "Lovelace",
  "email": "ada@example.com",
  "owner_id": "3e3417d7e",
  "is_active": true,
  "tags": {}
}
```

## 6. Portfolio

The tenant. Everything a customer thinks of as “our workspace” hangs off this id: orgs, teams, installed tools, files, data rings, scheduler jobs.

### Create funnel (`create_portfolio_funnel`)

`POST /_auth/portfolios` does not only insert a portfolio row. In order:

1. Create the **portfolio** entity (`name`, optional `about` / `tags` from the body).
2. Create a default **team** named `Admin` with `about` = “This team enables its users to change portfolio settings.” Nested under the new portfolio id.
3. Create `team:portfolio` (needed to walk user → team → portfolio).
4. Create `team:user` and `user:team` for the signed-in creator.

Older code that also installed an `_auth` tool, default roles, and a “First Org” is **commented out**. A new portfolio has **no orgs and no tools** until someone creates them.

Funnel success payload is a **transaction list** (each step’s response), not a single portfolio document:

```json
{
  "success": true,
  "message": "Create Portfolio Funnel completed, Ok",
  "status": 200,
  "document": [
    { "success": true, "message": "Entity created", "document": { "_id": "a1b2c3d4e5f6", "type": "portfolio", "name": "Acme" } },
    { "success": true, "message": "Entity created", "document": { "_id": "f6e5d4c3b2a1", "type": "team", "name": "Admin" } },
    { "success": true, "message": "Rel created", "document": { "index": "irn:rel:team:portfolio:f6e5d4c3b2a1:*", "rel": "a1b2c3d4e5f6" } },
    { "success": true, "message": "Rel created", "document": { "index": "irn:rel:team:user:f6e5d4c3b2a1:*", "rel": "3e3417d7e" } },
    { "success": true, "message": "Rel created", "document": { "index": "irn:rel:user:team:3e3417d7e:*", "rel": "f6e5d4c3b2a1" } }
  ]
}
```

The new portfolio id is `document[0].document._id`. After success the route **refreshes the auth tree**.

### List

`GET /_auth/portfolios` calls `list_entity('portfolio', user_id=...)`. Implementation:

1. Query `irn:rel:user:team:{user_id}:*`
2. For each team id, query `irn:rel:team:portfolio:{team_id}:*`
3. Return that list of **rel query responses** (not hydrated portfolio documents)

Clients that need names should `GET /_auth/portfolios/{id}` per id, or (preferred) read `GET /_auth/tree`, which already hydrates names.

### Get / update

- `GET /_auth/portfolios/{portfolio_id}` — entity document.
- `PUT /_auth/portfolios/{portfolio_id}` — merge `payload` into the document, then refresh the tree. Body is the payload itself (`name`, `about`, `tags`, …).

There is no delete-portfolio funnel.

## 7. Org

An org is a **data and access boundary inside a portfolio**. Files, data documents, chat, and most extension handlers take `(portfolio, org, ...)`.

The org entity is nested: you cannot look up an org by `org_id` alone. `get_entity('org', ...)` requires both `portfolio_id` and `org_id`.

### Create funnel (`create_org_funnel`)

Requires `name` and `portfolio_id`. Sets:

```python
kwargs["handle"] = self.generate_handle(kwargs["name"])
```

`generate_handle` keeps only **uppercase A–Z and digits**, then truncates to 10 characters:

```python
handle = re.sub(r"[^A-Z0-9]", "", name)[:10]
```

| `name` | `handle` |
|---|---|
| `Acme Building 12` | `AB12` |
| `First Org` | `FO` |
| `warehouse` | `""` (no capitals or digits) |

Prefer names with capitals if the handle is shown in URLs or UI. The funnel does **not** create any team/org or tool/org rels. The org exists but is **inactive** in the auth tree until a team is granted a tool in that org (`team/tool:org`).

No `portfolio:org` rel. Listing orgs is a query on `irn:entity:portfolio/org:{portfolio_id}/*`.

### HTTP

Composed id `{portfolio_id}-{org_id}` (split on first `-`):

| Method | Path | Notes |
|---|---|---|
| `POST` | `/_auth/orgs/{portfolio_id}` | Body must include `name` |
| `GET` | `/_auth/orgs/{portfolio_id}-{org_id}` | Hydrated entity |
| `PUT` | `/_auth/portfolios/{portfolio_id}/orgs/{org_id}` | Allowlisted `name`, `tags`; canonical update |
| `PUT` | `/_auth/orgs/{portfolio_id}-{org_id}` | Alternate; body is merged into kwargs (see [status notes](#18-status-notes)) |
| `DELETE` | `/_auth/portfolios/{portfolio_id}/orgs/{org_id}` | Calls `remove_org_funnel`, which is a **stub** (does not delete) |

Example create:

```http
POST /_auth/orgs/a1b2c3d4e5f6 HTTP/1.1
Authorization: Bearer eyJ...
Content-Type: application/json

{ "name": "Downtown Site", "about": "Main campus" }
```

## 8. Team

A team is the **unit of membership and grants**. Users never receive tool roles directly. To give Ada “editor on Data in Downtown Site”, put Ada on a team, assign Data to that team, assign the `editor` role, then grant that tool in that org.

### Nesting vs graph

The team **document** is stored under the portfolio:

```text
index = irn:entity:portfolio/team:{portfolio_id}/*
```

Core still writes `team:portfolio` because listing a user’s portfolios and building the auth tree start from **team id**, not from the team document’s `index`. Comments in the funnel (“you don’t need a Portfolio:Teams rel”) mean there is no reverse `portfolio:team` edge; children are listed by entity index.

### Create funnel (`create_team_funnel`)

Requires `name` and `portfolio_id`. Then:

1. Create team entity (creator is `owner_id`)
2. `team:portfolio`
3. `team:user` + `user:team` for the signed-in user (first member)

A brand-new team has **no tools, no roles, no orgs**.

### Membership

| Operation | Mechanism |
|---|---|
| List members | `GET /_auth/teams/{team_id}/users` — caller must already be on the team |
| Add existing Cognito user | Invite POST: if email is in the pool, `add_user_to_team_funnel` (both rels), no email |
| Add new person | Invite email + `PUT /_auth/user/invite` (see invites) |
| Remove | `DELETE /_auth/teams/{team_id}/users/{user_id}` — cannot remove yourself |

`team_id` on membership routes is **not** composed with portfolio id.

### Delete (`remove_team_funnel`)

1. Soft-delete the team entity (`unlink_entity` → `irn:unentity:portfolio/team:...`)
2. Delete `team:portfolio` rels
3. Delete `team:user` and `user:team` for every member
4. Delete `team:org` rels

It does **not** currently delete `team:tool`, `team/tool:role`, or `team/tool:org`. Those edges can remain as orphans after the team document is unlinked.

### HTTP

| Method | Path | Notes |
|---|---|---|
| `POST` | `/_auth/teams/{portfolio_id}` | Body must include `name` |
| `GET` | `/_auth/teams/{portfolio_id}-{team_id}` | Marked **not used** in the route |
| `PUT` | `/_auth/portfolios/{portfolio_id}/teams/{team_id}` | Allowlisted `name`, `tags` |
| `PUT` | `/_auth/teams/{portfolio_id}-{team_id}` | Alternate composed update |
| `DELETE` | `/_auth/portfolios/{portfolio_id}/teams/{team_id}` | Unlink + rel cleanup above |

## 9. Tool

A tool entity is **not** the extension source code. It is a **per-portfolio installation**: a row that says “this tenant has Data (or Schd) enabled,” plus the **catalog of roles** that installation supports.

### Install catalog (API)

`POST /_auth/portfolios/{portfolio_id}/tools` does not accept an arbitrary name. Body `name` is a **handle key** into a hardcoded catalog:

```python
valid_tools = {
    "data": {
        "name": "Data",
        "handle": "data",
        "about": "Data explorer",
        "roles": ["viewer", "editor", "admin"],
    },
    "schd": {
        "name": "Schd",
        "handle": "schd",
        "about": "Scheduler",
        "roles": ["operator", "admin"],
    },
}
```

Unknown keys return **403 Invalid Tool**. On match, Core stores the display `name`, `handle`, `about`, and `roles` on the new tool entity (`create_tool_funnel` → `create_entity('tool')`).

`roles` on the **tool entity** is the catalog (what may be assigned). Assigned roles live on **rels** `team/tool:role`, not on the tool document.

Installing a tool does **not** grant it to any team. Grants are later:

| Rel | Meaning |
|---|---|
| `team:tool` | This team may use the tool |
| `team/tool:role` | This team has this role on the tool (must be in the catalog) |
| `team/tool:org` | This team may use the tool **in this org** (makes the org `active` in the tree) |

After `team/tool:org` is created, Core calls the extension’s `initialize_extension` handler (config, jobs). That is post-grant setup, not entity CRUD.

### Get / rename / unlink

| Method | Path |
|---|---|
| `GET` | `/_auth/portfolios/{portfolio_id}/tools/{tool_id}` (marked not used) |
| `PUT` | `/_auth/portfolios/{portfolio_id}/tools/{tool_id}` — `name`, `tags` |
| `DELETE` | `/_auth/portfolios/{portfolio_id}/tools/{tool_id}` — `remove_tool_funnel` |

`remove_tool_funnel` **only unlinks the tool entity**. Cleanup of team/tool rels is commented out.

Example install:

```http
POST /_auth/portfolios/a1b2c3d4e5f6/tools HTTP/1.1
Authorization: Bearer eyJ...
Content-Type: application/json

{ "name": "data" }
```

Response `document` is a transaction list; the tool id is the created entity `_id`. The handle stored is `data`, which `authorize(..., tool_id="data")` can resolve from the tree.

## 10. Pseudo-org `_all`

`AuthController.PORTFOLIO_SCOPE_ORG = "_all"`.

`_all` is **not** an org entity. It is not written to DynamoDB. `normalize_auth_tree` injects it into every portfolio node of the auth tree so portfolio-scoped rings (config, some schd tools) have an org key.

| Property | Entity org | `_all` |
|---|---|---|
| Row in `{env}_entities` | Yes | No |
| `get_entity('org', org_id='_all')` | 404 | 404 (same) |
| In auth tree `portfolios[p].orgs` | Yes, if the document exists | Always, after normalize |
| `active` | True when some `team/tool:org` points at that org id | True when some grant uses `org_id=_all` |
| Org-level `authorize` | Requires that org `active` | Allowed if the user has **any** active real org |
| Tool-level `authorize` | Requires `team/tool:org` for that org | Still requires an explicit `_all` grant |

Never treat `_all` as “any org.” It is a sentinel for portfolio-wide data, not a wildcard.

## 11. How entities connect (minimum rels)

Entities answer *what exists*. Rels answer *who is attached*. For tenancy you need at least:

```text
user ──user:team / team:user──► team ──team:portfolio──► portfolio
                                      │
                                      ├── (entity index) ──► sibling orgs, tools
                                      └── team:tool, team/tool:role, team/tool:org
```

| Rel `index` | `rel` (SK) | Purpose |
|---|---|---|
| `irn:rel:user:team:{user_id}:*` | `team_id` | User’s teams (start of “my portfolios”) |
| `irn:rel:team:user:{team_id}:*` | `user_id` | Team roster |
| `irn:rel:team:portfolio:{team_id}:*` | `portfolio_id` | Which tenant the team belongs to |
| `irn:rel:team:tool:{team_id}:*` | `tool_id` | Tool assigned to team |
| `irn:rel:team/tool:role:{team_id}/{tool_id}:*` | `role_id` | Role on that tool |
| `irn:rel:team/tool:org:{team_id}/{tool_id}:*` | `org_id` | Tool usable in that org (`_all` allowed) |
| `irn:rel:team:org:{team_id}:*` | `org_id` | Legacy team↔org; still deleted with the team |

Same-portfolio guards (`is_user_team_same_portfolio`, `is_user_team_org_same_portfolio`) walk these edges so a team in portfolio A cannot be pointed at an org in portfolio B.

## 12. CRUD in Core

All entity I/O goes through `AuthController` then `AuthModel`.

### Get

```python
AUC.get_entity("org", portfolio_id="a1b2c3d4e5f6", org_id="c0ffee12aabb")
# { "success": True, "document": { ... }, "status": 200 }
```

Missing keys → `{success: False, message: "Some parameters are missing", status: 500}`. Missing item → `404`.

### List

| Type | How |
|---|---|
| portfolio | Walk `user:team` → `team:portfolio` (not an entity query) |
| org / team / tool | `query` on the nested `index` |
| user | No list-all-users API |
| `app` | Leftover index `irn:entity:team/app:{team_id}/*` — unused |

### Create

`create_entity` is rarely called from routes directly. Funnels wrap it so required rels exist:

| Funnel | Creates |
|---|---|
| `create_user_funnel` | User entity only |
| `create_portfolio_funnel` | Portfolio + Admin team + membership rels |
| `create_org_funnel` | Org entity + handle |
| `create_team_funnel` | Team + `team:portfolio` + creator membership |
| `create_tool_funnel` | Tool entity only |

Funnels are **not** DynamoDB transactions. A failure after step 1 can leave a portfolio without an Admin team (or similar). There is no automatic rollback except Cognito user create-with-password (identity, not tenancy).

### Update

`update_entity`:

1. `get_entity`; if 404 and type is `user`, run `create_user_funnel`; otherwise **400 Nothing to update**
2. For users, fill empty `name` / `slot_a` / `email` from kwargs (JWT backfill)
3. Merge `kwargs['payload']` onto the document (`tags` go through `sanitize_entity_tags`)
4. `put_item` (full document replace)

Callers must pass `payload`. Nested HTTP PUTs build that dict. Composed PUTs that dump the JSON body into kwargs only work if the client sent a `payload` property.

### Soft delete (`unlink_entity`)

```python
# index irn:entity:portfolio/team:{pid}/*  →  irn:unentity:portfolio/team:{pid}/*
undoc = copy.deepcopy(doc)
parts = undoc["index"].split(":")
parts[1] = "unentity"
undoc["index"] = ":".join(parts)
undoc["modified"] = datetime.now().isoformat()
AUM.create_entity(undoc)
AUM.delete_entity(**doc)
```

`get_entity` / `list_entity` query `irn:entity:...`, so unlinked rows disappear from the live API. A garbage collector is expected to use `modified` to hard-delete `unentity` later; Core does not run that collector.

Used by `remove_team_funnel` and `remove_tool_funnel`. **`remove_org_funnel` is unimplemented** (returns success without writing).

## 13. Tags

`tags` is `dict[str, list[str]]`. `sanitize_entity_tags`:

- Non-dict → `{}`
- Keys must be strings; stripped and **lowercased**; injection characters dropped
- Values coerced to a deduplicated list of safe strings
- Characters rejected: `{ } ; : / ' " \ ( ) [ ] $ | & < >`

```python
from renglo.common import sanitize_entity_tags

sanitize_entity_tags({"Locale": "en", "tier": ["pro", "pro"]})
# {"locale": ["en"], "tier": ["pro"]}
```

HTTP routes that allow tags (`PUT` user/portfolio/org/team/tool) sanitize before `update_entity`.

## 14. HTTP API

Prefix `/_auth`. All of these require `@cognito_auth_required`. Mutating routes that change the graph call `refresh_tree()` on success.

Route-level `authorization_check` currently always allows; a valid JWT is still required.

### Portfolios

| Method | Path | Funnel / method |
|---|---|---|
| `GET` | `/portfolios` | `list_entity('portfolio')` — rel walk |
| `POST` | `/portfolios` | `create_portfolio_funnel` |
| `GET` | `/portfolios/{portfolio_id}` | `get_entity` — **returns the document** on success |
| `PUT` | `/portfolios/{portfolio_id}` | `update_entity` + tree refresh |

### Orgs

| Method | Path | Funnel / method |
|---|---|---|
| `POST` | `/orgs/{portfolio_id}` | `create_org_funnel` (`name` required) |
| `GET` | `/orgs/{portfolio_id}-{org_id}` | `get_entity` — document on success |
| `PUT` | `/portfolios/{portfolio_id}/orgs/{org_id}` | `update_entity` (`name`, `tags`) |
| `DELETE` | `/portfolios/{portfolio_id}/orgs/{org_id}` | `remove_org_funnel` (**stub**) |

### Teams

| Method | Path | Funnel / method |
|---|---|---|
| `POST` | `/teams/{portfolio_id}` | `create_team_funnel` (`name` required) |
| `PUT` | `/portfolios/{portfolio_id}/teams/{team_id}` | `update_entity` (`name`, `tags`) |
| `DELETE` | `/portfolios/{portfolio_id}/teams/{team_id}` | `remove_team_funnel` |
| `GET` | `/teams/{team_id}/users` | `get_team_users` |
| `DELETE` | `/teams/{team_id}/users/{user_id}` | `remove_user_from_team_funnel` |

### Tools

| Method | Path | Funnel / method |
|---|---|---|
| `POST` | `/portfolios/{portfolio_id}/tools` | Catalog + `create_tool_funnel` |
| `PUT` | `/portfolios/{portfolio_id}/tools/{tool_id}` | `update_entity` (`name`, `tags`) |

| `POST`/`DELETE` | `.../orgs/{org_id}` | `assign_team_tool_orgs` (+ `initialize_extension` on POST) |

## 15. Worked examples

### 15.1 Create a tenant from scratch (library)

```python
from renglo.auth.auth_controller import AuthController

auc = AuthController(config=config)
user_id = auc.get_current_user()

created = auc.create_portfolio_funnel(
    name="Acme",
    about="Acme workspace",
    user_id=user_id,
)
portfolio_id = created["document"][0]["document"]["_id"]

org = auc.create_org_funnel(name="Downtown Site", portfolio_id=portfolio_id, user_id=user_id)
org_id = org["document"][0]["document"]["_id"]

team = auc.create_team_funnel(name="Editors", portfolio_id=portfolio_id, user_id=user_id)
team_id = team["document"][0]["document"]["_id"]

tool = auc.create_entity(
    "tool",
    portfolio_id=portfolio_id,
    user_id=user_id,
    name="Data",
    handle="data",
    about="Data explorer",
    roles=["viewer", "editor", "admin"],
)
tool_id = tool["document"]["_id"]
```

## 16. Downstream use of portfolio and org

Application data is **not** stored on these entities. Other Core tables key by the same ids:

| System | Typical key |
|---|---|
| Data documents | `(portfolio, org, ring, doc_id)` on `{env}_data` |
| Files | S3 prefix `_files/{portfolio}/{org}/{ring}/...` |
| Search | `{portfolio}#{org}#{ring}#{token}` |
| Session / chat | indexes that include portfolio and org |
| `authorize(portfolio, org, resource=..., tool_id=...)` | Auth tree for that user |

Handlers receive `payload["portfolio"]` and `payload["org"]`. Use real org ids for tenant data. Use `_all` only for portfolio-scoped rings that Core already treats as such.

## 18. Status notes

| Item | Status |
|---|---|
| Five entity types + nested IRNs | Live |
| Portfolio create → Admin team + creator membership | Live |
| Org / team / tool create | Live |
| Tool install catalog | **Data** and **Schd** only (API hardcoded) |
| Default org on new portfolio | Removed (commented out in the funnel) |
| `GET /portfolios` | Returns nested rel responses, not portfolio documents |
| `remove_org_funnel` | Stub; DELETE org does not remove the entity |
| `remove_team_funnel` | Unlinks team; does not clear tool/role/org-tool rels |
| `remove_tool_funnel` | Unlinks tool only; team/tool rels may remain |
| `list_entity('app')` | Leftover unused type |
| Composed `PUT /orgs/{id}` and `PUT /teams/{id}` | Pass JSON as kwargs; `update_entity` requires `payload` — prefer nested `/portfolios/...` PUTs |
| `authorization_check` on these routes | Stub (always allow) |
| Funnel atomicity | Not a DynamoDB transaction |
| `_all` | Tree-only; never an entity row |

Tenancy entities answer *what containers exist*. Who may use a tool in an org is the access graph and the auth tree, documented next.
