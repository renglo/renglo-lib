# Access graph (relationships)

Renglo access is a **directed graph of edges**, not fields nested inside entity JSON. Entities say *what exists* ([Tenancy model](tenancy-model.md)). Relationships say *who is attached to what*: membership, tenant placement, and tool grants.

This document is that graph: rel document shape, every `reltype` Core understands, how edges are created and deleted, and how walks such as “this user’s portfolios” and the auth tree are built. The compiled tree and `authorize()` are the next documents. Invites use two pending rel types; the full invite funnel is documented separately, but the edges live here.

## 1. Mental model

```
 user ──user:team──► team ──team:portfolio──► portfolio
                       │
                       ├── team:user (inverse roster)
                       ├── team:tool ──────────────────────────► tool
                       ├── team/tool:role ──► role id (viewer, admin, …)
                       └── team/tool:org ──► org id  (or "_all")
```

Rules that fall out of this shape:

- There is **no** `user:portfolio` edge. A person is in a tenant only by sitting on a team that has `team:portfolio`.
- There is **no** `user:tool` or `user:role`. Grants hang off **teams**. Ada is an editor on Data in Downtown because Ada is on Editors, Editors has Data + `editor`, and Editors has Data in Downtown.
- Org and tool **documents** are nested under the portfolio via entity `index` ([Tenancy](tenancy-model.md)). Access to them is **not** that nesting. An org is *active* for a user when some team they belong to has `team/tool:org` for that org.
- A rel is a tiny item: partition key + sort key. No names, no timestamps, no `from`/`to` objects. The type is encoded in `index`; the target id is `rel`.

Cardinality in code comments is “one to many”: one source (encoded in `index`) points at many targets (one row per `rel`). `team:portfolio` is modeled the same way even though a team almost always has a single portfolio.

## 2. Storage

| Config | Table | Keys |
|---|---|---|
| `DYNAMODB_REL_TABLE` | `{env}_rel` | `index` (PK, string) + `rel` (SK, string) |

Provisioned in `ops/launcher/cdk/stacks/storage.py` (`pk="index"`, `sk="rel"`).

A stored item is only:

```json
{
  "index": "irn:rel:user:team:3e3417d7e:*",
  "rel": "f6e5d4c3b2a1"
}
```

`AuthModel.create_rel` is `put_item`. Writing the same keys twice is idempotent (overwrite). `delete_rel` is `delete_item` on those two keys. There is no soft-delete (`unentity`) for rels: they are gone when deleted.

`list_rel(index)` queries `Key('index').eq(index)` with **Limit 50** (default). Tree assembly and `user_portfolios` use this helper, so a user on more than 50 teams (or a team with more than 50 tool/org grants under one `index`) can be **truncated**. Pagination’s `ExclusiveStartKey` uses attribute `ref`, but the sort key is `rel` — a second page would not work as written.

`list_rel_prefix(index, prefix)` is `begins_with` on the sort key. Invite accept uses it to find `email:code:...` without knowing TTL.

## 3. IRN convention

```text
index = irn:rel:{source_type}:{target_type}:{source_id}:*
rel   = {target_id}
```

Compound sources (a team **and** a tool) put a slash in the source type and a slash in the source id:

```text
index = irn:rel:team/tool:role:{team_id}/{tool_id}:*
rel   = {role_id}

index = irn:rel:team/tool:org:{team_id}/{tool_id}:*
rel   = {org_id}
```

The trailing `:*` is **literal** in the partition key, same idea as entity indexes. Listing all roles for a team/tool is a query on that exact `index`.

Invite edges are the exception: the whole triple sits on the **sort** key because TTL is not known at lookup time:

```text
index = irn:rel:email:hash:ttl:*:*:*
rel   = {email}:{hash}:{ttl}
```

`AuthController.create_rel(reltype, **data)` is the only place that maps a symbolic `reltype` (`'user:team'`, `'team/tool:org'`, …) onto `index`/`rel`. Callers should not concatenate IRNs by hand.

## 4. Rel type catalog

| `reltype` | `index` | `rel` | Meaning |
|---|---|---|---|
| `user:team` | `irn:rel:user:team:{user_id}:*` | `team_id` | This user is a member of this team |
| `team:user` | `irn:rel:team:user:{team_id}:*` | `user_id` | Inverse roster (list members from the team) |
| `team:portfolio` | `irn:rel:team:portfolio:{team_id}:*` | `portfolio_id` | This team belongs to this tenant |
| `team:tool` | `irn:rel:team:tool:{team_id}:*` | `tool_id` | This team may use this installed tool |
| `team/tool:role` | `irn:rel:team/tool:role:{team_id}/{tool_id}:*` | `role_id` | Assigned role (must be in the tool catalog on POST) |
| `team/tool:org` | `irn:rel:team/tool:org:{team_id}/{tool_id}:*` | `org_id` | Tool usable in this org (`_all` allowed) |
| `team:org` | `irn:rel:team:org:{team_id}:*` | `org_id` | Legacy team↔org; not what makes an org `active` |
| `email:hash:ttl` | `irn:rel:email:hash:ttl:*:*:*` | `{email}:{hash}:{ttl}` | Pending invite challenge (24h) |
| `hash:team` | `irn:rel:hash:team:{hash}:*` | `team_id` | Invite code → destination team |

Commented out, not implemented: `team/tool:action`. Roles replaced actions.

`get_rel` / `list_rel` use the same `reltype` strings. `list_rel` does not take a target id; it returns every `rel` under that `index`.

## 5. Membership

Membership is **two edges**. Creating only one of them breaks either “teams for this user” or “users for this team.”

```python
auc.create_rel("team:user", team_id=team_id, user_id=user_id)
auc.create_rel("user:team", team_id=team_id, user_id=user_id)
```

`add_user_to_team_funnel` writes both. `remove_user_from_team_funnel` deletes both. Portfolio and team create funnels also write both for the creator.

```text
PK  irn:rel:user:team:3e3417d7e:*     SK  f6e5d4c3b2a1     # Ada → Editors
PK  irn:rel:team:user:f6e5d4c3b2a1:*  SK  3e3417d7e        # Editors → Ada
```

`GET /_auth/teams/{team_id}/users` lists `team:user`, hydrates each user entity, and **rejects** the caller if their `user_id` is not in that map.

`DELETE /_auth/teams/{team_id}/users/{user_id}` refuses if the JWT user equals `user_id` (“You cannot remove yourself from a team”).

If the invitee **already exists in Cognito**, invite POST skips email and only runs `add_user_to_team_funnel`. New emails get pending invite rels instead ([§9](#9-pending-invite-edges)).

There is no unique constraint beyond the DynamoDB key. A duplicate add overwrites the same item.

## 6. Team placement (`team:portfolio`)

The team **entity** is already nested under the portfolio (`irn:entity:portfolio/team:{pid}/*`). The rel still exists because every user-centric walk starts from **team id**, not from the team document:

```text
user:team  →  team_id  →  team:portfolio  →  portfolio_id
```

`create_portfolio_funnel` and `create_team_funnel` both write this edge. `remove_team_funnel` deletes it.

`extension_config._portfolio_id_for_team` reads the first `team:portfolio` item to resolve which tenant a team is in (used after a grant, to load the tool handle).

A team with a missing `team:portfolio` row is invisible to `user_portfolios`, `GET /_auth/portfolios`, and `get_tree_full`, even if the team entity exists.

## 7. Grants (tool, role, org)

Three edges, usually applied in this order. None of them create the tool or org entity; those must already exist ([Tenancy](tenancy-model.md)).

### `team:tool` — team may use the tool

```http
POST   /_auth/teams/{team_id}/tools/{tool_id}
DELETE /_auth/teams/{team_id}/tools/{tool_id}
```

`assign_team_tools` writes or deletes `irn:rel:team:tool:{team_id}:*` → `tool_id`. No catalog check, no same-portfolio check. The tree copies these ids onto `teams[t].tools_access`.

### `team/tool:role` — named role on that tool

```http
POST   /_auth/teams/{team_id}/tools/{tool_id}/roles/{role_id}
DELETE /_auth/teams/{team_id}/tools/{tool_id}/roles/{role_id}
```

On **POST**, Core loads `team:portfolio` to find `portfolio_id`, loads the tool entity, and if that entity has a non-empty `roles` catalog, **rejects** a `role_id` that is not in it (`400 Role '…' is not defined for this tool`). Empty catalog → no check. DELETE skips the catalog.

Assigned roles are **not** stored on the tool document. Catalog = tool entity `roles`; assignment = this rel.

`authorize(..., resource='tool')` unions roles from **every** team of the user that has this tool in this org. Two teams can stack roles.

### `team/tool:org` — tool in an org (this is “active”)

```http
POST   /_auth/teams/{team_id}/tools/{tool_id}/orgs/{org_id}
DELETE /_auth/teams/{team_id}/tools/{tool_id}/orgs/{org_id}
```

`org_id` may be a real org `_id` or `_all`.

`get_tree_full` treats each of these edges as: that org is **active**, and that tool is listed on the org. `authorize` for `resource='org'` requires `orgs[o].active`. For `resource='tool'` it also requires this edge (a team of the user has the tool in that org).

No same-portfolio check in `assign_team_tool_orgs`. A mistaken `org_id` from another tenant would still write the row; the tree only hydrates orgs that exist under the current portfolio entity index, so a foreign org id would not become a named org node, but `_all` and stray ids can still appear in `teams[t].tools[tool].orgs`.

On successful **POST**, the route calls `initialize_assigned_extension` ([§14](#14-post-grant-initialize_extension)). DELETE does not un-initialize.

### What “Ada can edit Data in Downtown” looks like

Assume:

| Id | Value |
|---|---|
| Ada | `3e3417d7e` |
| Editors team | `f6e5d4c3b2a1` |
| Acme portfolio | `a1b2c3d4e5f6` |
| Downtown org | `c0ffee12aabb` |
| Data tool | `0da7a0001111` |

```text
user:team          3e3417d7e     → f6e5d4c3b2a1
team:user          f6e5d4c3b2a1  → 3e3417d7e
team:portfolio     f6e5d4c3b2a1  → a1b2c3d4e5f6
team:tool          f6e5d4c3b2a1  → 0da7a0001111
team/tool:role     f6e5d4c3b2a1/0da7a0001111 → editor
team/tool:org      f6e5d4c3b2a1/0da7a0001111 → c0ffee12aabb
```

Without `team/tool:org`, Downtown is listed as an org entity in the tree (all orgs under the portfolio are hydrated) but **not** `active`, so org-level authorize fails.

## 8. Legacy `team:org`

`irn:rel:team:org:{team_id}:*` → `org_id` is still in `create_rel` / `delete_rel`.

- `assign_team_orgs` writes it after `is_user_team_org_same_portfolio`. **There is no `/_auth` route** for this helper.
- Commented portfolio-funnel code used to create it with a default org.
- Some extension `*_onboardings.py` handlers still `create_rel('team:org', ...)`.
- `remove_team_funnel` tries to delete these rows (see [status notes](#17-status-notes) for a kwargs bug).

**Org activeness in the auth tree and in `authorize()` does not use `team:org`.** It uses `team/tool:org`. Treat `team:org` as leftover unless you are reading old onboarding code.

## 9. Pending invite edges

When the invitee is **not** in the Cognito pool, `invite_user_funnel` writes:

```python
ttl = self.generate_ttl(offset_min=1440)  # now + 24h, unix seconds
hash_ = self.generate_invite_hash(email, ttl)  # 6-digit numeric hash

self.create_rel("email:hash:ttl", email=email, hash=hash_, ttl=ttl)
self.create_rel("hash:team", hash=hash_, team_id=team_id)
```

```text
PK  irn:rel:email:hash:ttl:*:*:*     SK  ada@example.com:482913:1726400000
PK  irn:rel:hash:team:482913:*       SK  f6e5d4c3b2a1
```

Accept (`invite_create_user_funnel`) looks up with prefix `email:code` on the invite index (TTL unknown), checks expiry and hash, creates the Cognito user + user entity, then writes membership rels for each still-valid invitation.

These edges are **not** deleted after accept in the funnel. Stale invite rows can remain until TTL logic ignores them (`410 Invitation is expired`).

`delete_rel('hash:team', ...)` expects `data['team']`, not `data['team_id']` — inconsistent with create. Prefer not to call it until that is aligned.

## 10. Same-portfolio checks

Two helpers walk the membership graph, then test placement:

```python
def user_portfolios(self, user_id):
    # user:team items → for each team, team:portfolio items → unique portfolio ids
    ...

def is_user_team_same_portfolio(user_id=..., team_id=...):
    for portfolio_id in self.user_portfolios(user_id):
        if self.get_rel("team:portfolio", team_id=team_id, portfolio_id=portfolio_id)["success"]:
            return True
    return False

def is_user_team_org_same_portfolio(user_id=..., team_id=..., org_id=...):
    # same, plus get_entity("org", portfolio_id, org_id) must succeed
```

Used by:

| Caller | Check |
|---|---|
| `invite_user` (existing Cognito user) | `is_user_team_same_portfolio` (whether to treat them as already in-tenant; they are added to the team either way today) |
| `assign_team_orgs` | `is_user_team_org_same_portfolio` — reject if org is not in a portfolio the actor and team share |

Grant HTTP (`assign_team_tools`, roles, tool-org) does **not** call these helpers. Role assign only uses `team:portfolio` to load the tool catalog.

## 11. How the graph is walked

### User’s portfolios

```text
list user:team(user_id)
  for each team_id:
    list team:portfolio(team_id)
      collect rel (portfolio_id)
```

Used by `user_portfolios` and `list_entity('portfolio')` (`GET /_auth/portfolios`).

### Auth tree (`get_tree_full`)

For the signed-in user:

1. `user:team` → each `team_id`
2. `team:portfolio` → each `portfolio_id`; hydrate portfolio entity
3. Hydrate team entity; skip if unlinked/missing
4. `team:tool` → `tools_access`
5. List **all** tool entities under the portfolio (entity index, not rels)
6. For each tool: `team/tool:role` and `team/tool:org`
7. List **all** org entities under the portfolio; mark `active` if that org id appeared in step 6
8. Inject `_all` via `normalize_auth_tree`

So the tree mixes **rel walks** (what this user/team is granted) with **entity listings** (every org/tool that exists in the tenant). Existence ≠ access. Access is the rels.

Mutating `/_auth` routes that change rels or entities call `refresh_tree()` so the S3-cached tree does not stay stale. That compilation is the auth-tree document.

## 12. CRUD in Core

```python
auc.create_rel("team/tool:org", team_id=tid, tool_id=tool_id, org_id=org_id)
auc.get_rel("team/tool:org", team_id=tid, tool_id=tool_id, org_id=org_id)
auc.list_rel("team/tool:org", team_id=tid, tool_id=tool_id)
auc.delete_rel("team/tool:org", team_id=tid, tool_id=tool_id, org_id=org_id)
```

Controller maps `reltype` → `index`/`rel`, then `AuthModel` hits DynamoDB.

`list_rel` return shape:

```json
{
  "success": true,
  "message": "Documents found",
  "document": {
    "items": [
      { "index": "irn:rel:team:tool:f6e5d4c3b2a1:*", "rel": "0da7a0001111" }
    ],
    "lastkey": null
  },
  "status": 200
}
```

`list_rel_prefix` returns `document` as a **bare list** of items (not `{items, lastkey}`). Invite code verification depends on that.

Assign helpers wrap create/delete and take `method` `'POST'` | `'DELETE'`:

| Helper | Rel | Extra logic |
|---|---|---|
| `assign_team_tools` | `team:tool` | none |
| `assign_team_tool_roles` | `team/tool:role` | catalog check on POST |
| `assign_team_tool_orgs` | `team/tool:org` | none |
| `assign_team_orgs` | `team:org` | same-portfolio check |

## 13. HTTP API

All require `@cognito_auth_required`. `authorization_check` is currently a stub (always allow). Success responses return the **rel document** (`{index, rel}`) and refresh the auth tree.

| Method | Path | Rel |
|---|---|---|
| `POST` / `DELETE` | `/_auth/teams/{team_id}/tools/{tool_id}` | `team:tool` |
| `POST` / `DELETE` | `/_auth/teams/{team_id}/tools/{tool_id}/roles/{role_id}` | `team/tool:role` |
| `POST` / `DELETE` | `/_auth/teams/{team_id}/tools/{tool_id}/orgs/{org_id}` | `team/tool:org` |
| `DELETE` | `/_auth/teams/{team_id}/users/{user_id}` | both membership rels |
| `GET` | `/_auth/teams/{team_id}/users` | reads `team:user` |
| `POST` | `/_auth/user/invite` | membership **or** invite pending rels |

There is no GET that lists raw rels. The console reads `GET /_auth/tree`.

Example — grant Data + editor in Downtown, then undo org access:

```bash
TEAM=f6e5d4c3b2a1
TOOL=0da7a0001111
ORG=c0ffee12aabb

curl -sS -X POST "$API/_auth/teams/$TEAM/tools/$TOOL" \
  -H "Authorization: Bearer $TOKEN"

curl -sS -X POST "$API/_auth/teams/$TEAM/tools/$TOOL/roles/editor" \
  -H "Authorization: Bearer $TOKEN"

curl -sS -X POST "$API/_auth/teams/$TEAM/tools/$TOOL/orgs/$ORG" \
  -H "Authorization: Bearer $TOKEN"

curl -sS -X DELETE "$API/_auth/teams/$TEAM/tools/$TOOL/orgs/$ORG" \
  -H "Authorization: Bearer $TOKEN"
```

Success body:

```json
{
  "index": "irn:rel:team/tool:org:f6e5d4c3b2a1/0da7a0001111:*",
  "rel": "c0ffee12aabb"
}
```

## 14. Post-grant `initialize_extension`

After a successful **POST** `team/tool:org`, `auth_routes` calls `initialize_assigned_extension(config, team_id, tool_id, org_id)` (`renglo/auth/extension_config.py`):

1. Resolve portfolio via `team:portfolio`
2. Load tool entity → `handle` (`data`, `schd`, …)
3. Run `{handle}/initialize_extension` with `{portfolio, org, tool, tool_id}`
4. Bypass `@authorize` (the assignment was already accepted)
5. Log failures; **do not** delete the rel

Onboarding that only installs the tool on the portfolio is not enough. Per-org config and jobs start when this grant is written.

## 17. Status notes

| Item | Status |
|---|---|
| Bidirectional membership + `team:portfolio` | Live; required for tree and portfolio list |
| `team:tool` / `team/tool:role` / `team/tool:org` | Live; this is real access |
| Role catalog check | POST only; empty catalog allows any `role_id` |
| `team/tool:org` same-portfolio validation | **Not** done in `assign_team_tool_orgs` |
| `team:org` | Legacy; not used by `authorize` / org `active` |
| `assign_team_orgs` | Controller only; no HTTP route |
| Invite pending rels | Live; not deleted after accept |
| Rel document metadata | None (no `modified`, actor, or TTL attribute except inside invite SK) |
| `list_rel` default limit | 50; tree/portfolio walks can truncate |
| `list_rel` pagination key | Uses `ref`; sort key is `rel` |
| `delete_rel('hash:team')` | Expects `team`, create uses `team_id` |
| `remove_team_funnel` `team:org` delete | Passes `user_id=org['rel']` instead of `org_id` — can KeyError |
| Team/tool unlink funnels | Do not fully delete grant rels ([Tenancy](tenancy-model.md) status) |
| `authorization_check` on grant routes | Stub |
| `team/tool:action` | Abandoned |

The access graph is the source of truth for membership and grants. The auth tree is a **cached projection** of this graph plus entity names. `authorize()` reads that projection, not Dynamo rels on each request.
